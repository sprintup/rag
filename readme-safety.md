# Safety and Security

This guide collects the safety and security points of this project in one place: the two rules
the presentation builds up to, and the other risks found while building it. Each section says
**where it applies in this project** and **what to do**.

> **This is an example project for learning, not a product.** The RAG app, the TinyLlama plugin,
> the skills, the Idea Generator agent and the toddler vocabulary activity exist to demonstrate how
> local models, harnesses and tools work. They aren't designed, tested or secured for production
> use, and they aren't educational products for children. Activities and answers generated by a
> small model can be wrong, inappropriate or unsafe. An adult must review anything before it's
> used with children. See section 10.

---

## The two rules

1. ⚠ **Disable tools by default.** In Agent mode, VS Code turns on every tool, 118 on this
   computer: editing files, running terminal commands, fetching web pages, acting on GitHub. Start
   with all tools off, enable only what a task needs, and keep approvals on.
   Details: "Security: start with every tool turned off" in
   [06_readme-mcp-agents.md](06_readme-mcp-agents.md), and "Security: why tools should be denied by
   default" in [05_readme-models.md](05_readme-models.md).
2. ⚠ **Be careful with `.md` files from public collections.** Agents, skills, prompt files and
   instructions files are plain Markdown that the model **follows as instructions**. They can hide
   injected instructions, or grant an agent broad tools. Read the raw file and its `tools:` list
   before using it. Details: "Security: public agents and skills can contain injections" in
   [06_readme-mcp-agents.md](06_readme-mcp-agents.md).

### 1. Local servers reachable from your network

"Running locally" doesn't automatically mean "only reachable from this computer". It depends on
which **network address** a program listens on:
- **`127.0.0.1` (localhost)** means only programs on this computer can connect.
- **`0.0.0.0` (all interfaces)** means any device that can reach your computer can connect, e.g.
  others on the same Wi-Fi, if the firewall lets them through.

In this project:
- **The Envie app (Streamlit) listens on all interfaces by default.** That's why it prints a
  *Network URL* as well as a *Local URL*. Someone on the same network could open the app, ask
  questions answered from **your uploaded documents**, and upload files, if Windows Firewall
  allowed Python in (it usually asks the first time). **Fix:** start it with
  `streamlit run src/main.py --server.address 127.0.0.1`, or create `.streamlit/config.toml` with:
  ```toml
  [server]
  address = "127.0.0.1"
  ```
- **The inference server** (`src/inference_server.py`) listens on `127.0.0.1` unless you set the
  `HOST` environment variable. Don't set it to `0.0.0.0`.
- **Ollama** listens on `127.0.0.1:11434` by default. The `OLLAMA_HOST` setting can change that;
  leave it unset.

**None of these servers ask for a password.** Anything that can reach them can use them. Keeping
them on `127.0.0.1` is what protects them.

### 2. Pickle files can run code when loaded

The Envie app saves its search index in `vectorstore/`, as `index.faiss` (the vectors) and
**`index.pkl`**, a Python **pickle** file. Pickle is Python's built-in way to save objects to a file
and load them back. Loading a pickle can **run any code** that was put into it, so a pickle from
someone else is as dangerous as running their program.

That's why the app has to opt in, in [src/main.py](src/main.py), with
`FAISS.load_local(..., allow_dangerous_deserialization=True)`. It's safe here, because the app only
loads the index it built itself from your own documents. But:
- **Never load a `vectorstore/` folder you didn't create:** shared with you, downloaded, or included
  in a cloned repository. If in doubt, delete `vectorstore/`; the app rebuilds it from
  `uploaded_docs/`.
- **Don't commit or share `vectorstore/`.** It's in `.gitignore`.
- The same applies to model files. Prefer **`.safetensors`**, which holds only numbers and can't run
  code, over older pickle-based `.bin`/`.pt` files, and avoid `trust_remote_code=True` for models from
  publishers you don't trust.

How pickles fit into the RAG pipeline is explained in
[02_readme-rag-user-guide.md](02_readme-rag-user-guide.md).

### 3. Model supply chain and bias

A downloaded model is someone else's work: its training data and fine-tuning shape what it says,
including its biases. A few hundred QLoRA examples on a home GPU can add a bias, and anyone can
publish the result. With Ollama (Ollama Inc.) or Foundry Local (Microsoft), the runtime provider
also chooses, converts and serves the model, so you're trusting them too.
- Download from the **original publisher** or the runtime's official library.
- Read the **model card**: who made it, what it was trained on, its license.
- **Test** a model on the questions you care about before relying on it.

Details: "Where the models come from" in [05_readme-models.md](05_readme-models.md), "Downloading
the model yourself vs. using Ollama" in [01_readme-setup.md](01_readme-setup.md), and
[readme-model-training.md](readme-model-training.md).

### 4. Unpinned downloads

Several commands fetch the **latest** version of something every time. If that release were
compromised, or just changed, you'd get it without noticing:

| Command | Risk | How to pin it |
|---|---|---|
| `uvx mcp-server-fetch` (in [.vscode/mcp.json](.vscode/mcp.json)) | A fresh install runs the newest release from PyPI | `"args": ["mcp-server-fetch==<version>"]`. Find versions on [PyPI](https://pypi.org/project/mcp-server-fetch/). |
| `npx @modelcontextprotocol/inspector` | Runs the newest release from npm | `npx @modelcontextprotocol/inspector@<version>` |
| `ollama pull qwen3.5:4b` | A tag can be updated to point to a different model | Note the **ID** from `ollama list`, and check it after pulling again |
| `hf download <model>` | The repository's newest files | `hf download <model> --revision <commit>` |

`requirements.txt` already pins exact versions for the Python libraries.

### 5. "Local" isn't automatically private

The model's answers are generated on your computer, but other parts of Copilot Chat may still use
the cloud:
- **Switching models mid-chat.** Changing from `qwen3.5:4b` to a GitHub model in the same
  conversation sends the **whole history**, including anything attached earlier
  (`#codebase`, files), to the cloud. Start a new chat instead.
- **Background "utility" jobs** may use GitHub models (see below) unless
  `chat.byokUtilityModelDefault` is set to *"Use the selected BYOK main agent model"* and
  `chat.useCopilotModelsForUtilityModels` is off.
- **Copilot itself** still contacts GitHub, e.g. for signing in.

**What's a utility model?** Besides the **main model** you pick in the model picker, Copilot Chat
uses a second, usually smaller model behind the scenes for small helper jobs, for example:
- writing the chat's **title** (e.g. *"User greeting"*),
- **compacting** a long conversation into a summary (*"Compacted conversation"*),
- narrowing down which **tools** to send (*"Optimized tool selection"*),
- suggesting follow-up questions or commit messages.

VS Code doesn't fully document the list. These jobs see parts of your conversation, so when the
main model is local (a "bring your own key", or BYOK, model such as `qwen3.5:4b`), a cloud utility
model can still send some of your chat to GitHub. The two settings above make Qwen do these jobs
too. The trade-off: titles and summaries are slower and rougher. (`chat.utilityModel` and
`chat.utilitySmallModel` choose a specific model instead.)

### 6. Logs and exports keep your prompts

Several debugging features save **full prompts**, including attached files, on disk: **Chat Debug
View** exports, **agent debug logs**, and Ollama with **`OLLAMA_DEBUG=1`**. Turn debug logging off
when you're done (`setx OLLAMA_DEBUG 0`, then restart Ollama), delete exports you no longer need,
and check them before sharing.

### 7. Credentials stored or used on your behalf

- **`hf auth login`** saves your Hugging Face token in plain text in your user folder
  (`%USERPROFILE%\.cache\huggingface\token`). Use a token with only the permissions you need, and
  delete it with `hf auth logout` when you're done.
- **MCP servers and extensions** such as GitHub act **as you**, with your signed-in account. A tool
  call can create issues or change repositories in your name. Keep them off unless needed (rule 1).
  For the GitHub MCP server, start **read-only** with a single toolset, e.g.
  `https://api.githubcopilot.com/mcp/x/issues/readonly` (see Part 5 of
  [06_readme-mcp-agents.md](06_readme-mcp-agents.md)).
- Never put tokens in code, prompts or committed files. `.env` is in `.gitignore`.

### 8. Fetched content can't be trusted

Anything the Fetch MCP server or `#fetch` brings in, such as web pages, can contain instructions
aimed at the model (prompt injection). Keep approvals on, so you see each URL before it's fetched,
and remember that a URL itself can carry data out. The Fetch server refuses private and local
addresses by default; don't turn that off (`--allow-private-ips`). Also respect sites' terms and
`robots.txt`: the two sites used here allow it, but many don't.
Details: "Safety" in [06_readme-mcp-agents.md](06_readme-mcp-agents.md).

### 9. Dev container and Codespaces settings

The dev container turns off Streamlit's XSRF protection, so that file uploads work through the
Codespaces proxy ([.devcontainer/devcontainer.json](.devcontainer/devcontainer.json)). That's
acceptable while the forwarded port stays **private**, the default, so only your GitHub account
can open it. Don't make the port public. Also open repositories you haven't reviewed in **Restricted
Mode** (*"Do you trust the authors of the files in this folder?"* → **No**), because their
`.github/` and `.vscode/` folders can bring agents, skills, MCP servers and hooks with them.

### 10. Children as the audience: an example, not a product

The Word of the Day activity ([06_readme-mcp-agents.md](06_readme-mcp-agents.md)) and the
vocabulary tutor ([readme-model-training.md](readme-model-training.md)) are **examples** of what the
technology can do. They are **not** products for teaching children, and haven't been reviewed by
educators or child-safety specialists.
- **Review everything first.** A small local model can produce wrong definitions, unsuitable
  content or unsafe activity ideas, even with the toddler-friendly instructions. An adult must
  check every activity before it's used, and supervise.
- **Protect children's privacy.** Don't put children's names, photos or personal details into
  prompts, and especially not into cloud models.
- **A real product would need much more:** age-appropriate design reviewed by educators,
  content-safety testing and filtering, privacy and data-protection compliance (for example,
  children's privacy laws such as COPPA in the US, or GDPR in Europe), accessibility, and ongoing
  monitoring.

## Checklist

Before a demo:
- [ ] All tools off in **Configure Tools**; only what each step needs turned on
- [ ] Approvals on: **Default permissions**, `chat.tools.global.autoApprove` off
- [ ] Any agent, skill, prompt or instructions file not written by you has been read (raw)
- [ ] The Envie app started with `--server.address 127.0.0.1`
- [ ] No `vectorstore/` from anywhere else
- [ ] A **new chat** for each step, with no switching between local and cloud models in one chat
- [ ] Debug logging off afterwards, and exports deleted

Before using anything here for real:
- [ ] Downloads pinned (section 4)
- [ ] Every generated activity reviewed by an adult (section 10)
- [ ] Remember: this is an example project, not a product
